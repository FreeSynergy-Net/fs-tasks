## 0.0.10

### English

- **Fix: `fs-tasks` opened no window and said nothing while a server held the socket and did not answer.** Cause (honest): the start had no time limit anywhere. The server binds its socket before it opens its store, and the kernel takes a connection into the backlog, so "a connect worked" counted as "a server is there"; the window then waited for the first answer without end, and the start lock was taken without a time limit. Now every wait of the start has a limit: the handshake (connect and `Control.version`, about 2 s per step), the start lock (try-lock, waiting 2 s), the first questions of a connection (5 s), the whole start (30 s). A server counts as there only when it **answered**.
- **A silent server is taken over, safely.** If a server holds the socket and does not answer, the client finds its process through the socket itself (`SO_PEERCRED`: the process that listens) and ends it only if all of this holds: same user; `/proc/<pid>/exe` is this program's file (the same file, or the same real path after an update; a name alone never counts); the start time of the process (`/proc/<pid>/stat`) is the same when it is found and again after a `pidfd` is taken (a reused process number is not hit); never process 1 and never itself. A server younger than 6 s may still be opening its store and gets until then. Then SIGTERM, after 2 s SIGKILL (through the `pidfd`), and only the socket file that belonged to that process is removed; every step is written to `<socket>.takeover.log` (pid, start time, program) and to stderr. A new server is started after that.
- **Otherwise it says so, and never stays silent.** A process of another user, with unreadable data or a reused number is not ended. **Another program is never ended, also not with a yes (even of the same user): only a message with PID, since and program (`other-program` reason), no button.** Only for a process that is provably this program the window opens and says **"Tasks is already running, but it does not answer (PID, since, program). End it?"** with two answers in its menu ("Yes: end it and start again" runs the take-over with the same rules, the process must still be the one shown; "No: close"); the status line says it too. Where no window is possible (command line, picture, no screen) the same goes to stderr. Every failure of the start has a code and parameters (`server-unresponsive` with `pid`, `since`, `exe`; `start-locked`; `other-program`; `start-failed`) and a sentence in German or English (by `LC_ALL`/`LANG`); exit code **3** for the window command, **4** for the command line (there 3 stays the claim conflict); both are in `--help`; 1 for the rest.
- **SIGTERM works before the store is open.** The server ends at the next wait if SIGTERM or Ctrl-C comes while it opens its store (`fs-interfaces` remembers the signal and acts only after `open`; that is a question for the library, here it is solved in the program). Limit: work that blocks without waiting still cannot be interrupted; SIGKILL of the take-over covers that.
- **capnp-rpc 0.27.5** (lock only, with capnp-futures 0.27.1): fixes the panic "message loop outlived connection state?" at shutdown. `capnp` stays at 0.27.
- Limits: the question is a menu with two entries, not a dialog (the shell has none yet); the take-over works on Linux (`/proc`, `pidfd`), elsewhere the start ends with the message and nothing is ended; a server of another version that answers is used as before (not replaced); the window that shows the message was checked at shell level (status, menus, handler) and as a picture where a graphics adapter exists, not on a real screen.
- **Fix: a task typed in the entry line disappeared from the view when the view was filtered.** The task was made, but the entry line did not take over the filter of the view: on the board with a project chosen the new task had no project and was hidden at once; in the day list, a task typed in Upcoming, Someday or Logbook did not belong in that list. Now a new task takes what the view gives it (one rule for all views, `defaults_for`): the board gives the project (label) chosen and the status of the column; Today gives today, Upcoming gives tomorrow, a project list gives the project; Inbox and Anytime give nothing (they show it as it is). Where a view cannot hold a new task (Someday, Logbook: a new task is neither blocked nor finished) the screen says so: "Created \"X\" in Inbox, not in the current filter." (code `task.created-outside-view`, parameters title and place; German or English by `LC_ALL`/`LANG`).
- **Refusals are visible.** A failed create, move or tick used to be swallowed (the line looked as if it had vanished). Now the screen shows the message with code and parameters (`task.create-failed`, `task.change-failed`; kind and the store's words); a failed create names the typed text in the message.
- Limits: the message stands in the side list of the board (only when the window is wide enough to show it) and in the note of the day list; the typed text is not put back into the entry line, because the entry widget of `fs-components` v0.0.13 clears itself before the program is asked and has no way to set its text; the program keeps it in the message instead. Tested without a window (the screens over the real core); not with a person at a screen.

Grenze: Arbeit, die ohne Warten blockiert, lässt sich weiterhin nicht unterbrechen; das SIGKILL der Übernahme deckt das ab.
- **capnp-rpc 0.27.5** (nur Sperrdatei, mit capnp-futures 0.27.1): behebt den Panic „message loop outlived connection state?“ beim Beenden. `capnp` bleibt auf 0.27.

## 0.0.9

### English

- **Fix: the program did not start when its data folder existed with mode 0755.** The window of 0.0.8 made `~/.local/share/freesynergy/tasks` with the default mode (0755) before the server ran; the transport of the server wants 0700 and refused it, and the client only said "run `fs-tasks serve` to see why". Now: (1) the window, the server and the client make their folders with 0700 (`freesynergy` and below; `~/.local/share` itself keeps its ordinary mode); (2) the server **corrects** an open data folder of its own before it starts: only bits are taken away (to 0700), only for a folder of this user that is not a link and is a directory, on the opened folder itself (not the path), checked again afterwards; what is inside is not changed, the folders above are still only checked. It says so in its log (`data-dir-tightened`, folder, old mode, "was open, may have been read"); a private folder gives no message. A link, a file, a folder of somebody else or a folder that stays open is refused with a code and parameters (`data-dir-symlink`, `-not-directory`, `-foreign-owner`, `-io`, `-still-open`) and a sentence in German or English (by `LC_ALL`/`LANG`).
- **Start errors are visible.** A server started by a client writes what it says to `<socket>.log` (mode 0600, one file per program, overwritten at each start, cut to its last 64 KB when the start error is read); a start error now shows the last ten lines, so the cause stands there (for example `PermissionDenied`), not only a hint.
- Limits: a server that runs for a very long time can write more than 64 KB before the next start; the window shows the start error on the terminal (stderr) and in its exit message, not in a dialog; the fix of the library (`fs-interfaces`, pinned at v0.0.22) is not done here: the correction is local to this program. The server corrects only its standard data folder (`$XDG_DATA_HOME/freesynergy/tasks`), never one named with `--data`, and only if the folders above it are safe (a folder above that others can write is refused as `data-dir-ancestor`, with the sentence in the program).

## 0.0.8

### English

- **Work board: workers work through fs-tasks.** New commands (all with `--json`, exit codes 0 ok / 1 error / 2 wrong words / **3 conflict**, no ANSI): `claim <id> --as NAME [--until 2h]`, `release`, `next --as NAME [--project P]` (the first ready task, claimed in one step), `status <id> in-progress|done|failed [--note] [--report] [--cost]`, `note <id> <text>` (500 bytes), `check <id>`, and `add` / `list` with `--project`, `--objective CMD` / `--subjective`, `--as`, `--status`. `failed` is the existing JSCalendar progress `failed` (no change on the wire); the board shows it as a column. The protocol is in `docs/worker-protocol.md` (EN + DE, with a runner wrapper).
- **One store, no server by hand.** Every command starts `fs-tasks serve` (in its own process group) if no server answers; a lock file next to the socket makes many clients at once start one server. The window now keeps its tasks in `objects.db` of the data folder, the file the server uses (an old `app.db` is moved there); the window is a **client** of that one server (`--connect <socket>`; it starts the server if none runs and never opens the data file itself), so workers and the board work on one repository, and closing the window leaves the server running. The board and the day list follow changes of other clients at once (the server's change feed, no polling); the classic frontend does not: it reads its list again only at its next action (limit: it needs a reload function in `fs-components`, which this repository cannot add). Claims are `editIf` (compare and set on the revision) and read again after a lost race.
- **Check commands are code.** `check` runs a task's command only if the task was made on this machine (`origin` local; every import is `imported`) by a trusted actor, and only for allowed programs (`cargo`, `fs-release`, `bash scripts/...`; settings in `check-policy.json`); as an argument list, no shell, time limit, output bounded. Otherwise `check command not run: foreign origin` (exit 1, task unchanged, `done` refused). `done` of an objective task needs the passed check. Titles, notes, reports and commands with obvious secrets (`sk-ant-`, `ghp_`, `-----BEGIN`, `Bearer `) are refused.
- **Renamed: "Face" is now "Frontend".** The menu is **Frontend** (entries Classic, Board, Day list), the help and messages say frontend, the code too (`Frontend`, `Frontends`, `FrontendOptions`, `Plan::frontend`, menu entry ids `frontend-…`). The remembered choice in `settings.json` is kept under the key `frontend`; a file of an older version with the key `face` is read once and rewritten atomically with `frontend` (the old key stays in the file). No other behaviour changed.
- Project = label `project:<name>`; `list --project`, and the board's search field finds it (type `project:name`).
- A check that runs too long is ended with its whole process group (Unix; Windows: only the child, documented limit). `--connect` and all other window options are checked against the dispatch of `fs-tasks` by a test that starts the real program.
- **Fixes in the same version:** the window saves and moves with compare-and-set; calls over the socket end after 10 s with a message; a check whose grandchild keeps the output open no longer hangs (0.5 s, then the group is ended and an error is reported); `kill` is run from a fixed path and a failure is reported; the live handle of the board is weak.
- Limits: the window does not reconnect if the server dies (restart the window); `claim`, `assign_actor`, paging by place are not on the wire (not available to the window). The `done` gate is a rule of the command line, not of the core (the board moves cards freely). No sync: the claim is a note for this machine. Tested with the real program and pictures of the window and at the cache level; not with a person at a screen.

Claims laufen über `editIf` (Vergleichen und Setzen auf der Revision), nach verlorenem Wettlauf wird neu gelesen.
- **Prüfbefehle sind Code.** `check` führt den Befehl einer Aufgabe nur aus, wenn sie auf diesem Rechner angelegt wurde (`origin` local; jeder Import ist `imported`) und von einem vertrauten Akteur stammt, und nur für erlaubte Programme (`cargo`, `fs-release`, `bash scripts/...`; Einstellung `check-policy.json`); als Argumentliste, ohne Shell, mit Zeitlimit und begrenzter Ausgabe. Sonst `check command not run: foreign origin` (Exit 1, Aufgabe unverändert, `done` abgelehnt). `done` einer objektiven Aufgabe braucht den bestandenen Check. Offensichtliche Geheimnisse in Titel, Notiz, Bericht und Befehl werden abgelehnt.
- **Umbenannt: „Gesicht/Face“ heißt jetzt „Frontend“.** Das Menü heißt **Frontend** (Einträge Classic, Board, Day list), Hilfe und Meldungen sagen Frontend, der Code ebenso (`Frontend`, `Frontends`, `FrontendOptions`, `Plan::frontend`, Menü-Ids `frontend-…`). Die gemerkte Wahl in `settings.json` liegt unter dem Schlüssel `frontend`; eine Datei einer älteren Version mit dem Schlüssel `face` wird einmal gelesen und atomar mit `frontend` neu geschrieben (der alte Schlüssel bleibt in der Datei). Sonst ändert sich nichts.
- Projekt = Label `project:<name>`; `list --project`, und das Suchfeld des Boards findet es (`project:name` tippen).
- Ein Prüfbefehl, der zu lange läuft, wird mit seiner ganzen Prozessgruppe beendet (Unix; Windows: nur das Kind, dokumentierte Grenze). Alle Fensteroptionen werden von einem Test mit dem echten Programm gegen den Dispatch von `fs-tasks` abgeglichen.
- **Korrekturen in derselben Version:** das Fenster speichert und verschiebt mit Vergleichen-und-Setzen; Aufrufe über den Socket enden nach 10 s mit einer Meldung; ein Prüfbefehl, dessen Enkel die Ausgabe offen hält, hängt nicht mehr (0,5 s, dann wird die Gruppe beendet und ein Fehler gemeldet); `kill` läuft über einen festen Pfad, ein Fehlschlag wird gemeldet; der Verweis des Boards auf die Änderungen ist schwach.
- Grenzen: das Fenster verbindet sich nicht neu, wenn der Server stirbt (Fenster neu starten); `claim`, `assign_actor`, Seiten nach Ort sind nicht auf der Leitung (dem Fenster nicht verfügbar). Das `done`-Tor ist Regel der Kommandozeile, nicht des Kerns (das Board verschiebt Karten frei). Kein Sync: der Claim ist eine Notiz für diesen Rechner. Getestet mit dem echten Programm und Bildern des Fensters sowie auf Cache-Ebene, nicht mit einer Person am Bildschirm.
